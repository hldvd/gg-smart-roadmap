# software-overview.md — خلاصه معماری نرم‌افزار G&G^SMART

## خلاصه

این سند خلاصه‌ای از معماری نرم‌افزار پروژه G&G^SMART است.

**منبع:** اسناد معماری نرم‌افزار + کد منبع پروژه.

**⚠️ هشدار مهم:** پروژه دارای **دو نسخهٔ کدی** است و هنوز معلوم نیست کدامیک مرجع است
(`g-vs-bly` و `g-vs-bly-loc1` — جدول مقایسه در پایین). مواردی که فقط در یک نسخه هستند با برچسب مشخص شده‌اند.

- این ترتیب درستی است و باید حفظ شود

## ۲. چرخهٔ اجرا

```
setup()
  → Serial.begin(115200)
  → registerBlynkHandlers()      (برای جلوگیری از حذف شدن توسط لینکر)
  → SystemManager::begin()

SystemManager::begin():
  1. Hardware::begin()      مقداردهی پین‌ها
  2. state.begin()          مقداردهی وضعیت
  3. devices.begin()        راه‌اندازی تجهیزات
  4. sensors.begin()        راه‌اندازی سنسورها
  5. automation.begin()     ریست تایمرها
  6. network.begin()        WiFi + NTP
  7. blynk.begin()          پیکربندی Blynk
  (+ webUI.begin() — فقط در نسخهٔ `loc1`)

loop()
  → SystemManager::update():
      1. network.update()     بررسی اتصال WiFi
      2. devices.update()     وضعیت تجهیزات
      3. sensors.update()     خواندن سنسورها
      4. blynk.update()       پردازش Blynk + ارسال داده
      5. automation.update()  تصمیم‌گیری خودکار
      6. state.update()       به‌روزرسانی وضعیت
      (+ webUI.update() — فقط در نسخهٔ `loc1`)
```

## ۴. وضعیت سیستم (`StateManager`)

فیلدهای واقعی (طبق کد):

| فیلدها | توضیح |
|---|---|
| `light`, `fan`, `fogger`, `pump` | وضعیت هر تجهیز |
| `temperature`, `humidity` | دادهٔ DHT22 |
| `waterLevelPercent` | سطح آب (٪) |
| `waterEmpty` | هشدار خالی‌شدن مخزن (با هیسترزیس) |
| `lastValidSensorReadMs` | آخرین خواندن معتبر DHT |
| `safeMode` | حالت ایمن |
| `wifiConnected`, `blynkConnected` | وضعیت اتصال |
| `autoMode` | `true` = AUTO، `false` = MANUAL |

> ⚠️ متغیرهای `systemMode`، `lastUpdate`، `errorFlags`، `systemHealth` و متدّهای
> `getHealth()`/`setMode()` که در نسخهٔ قبلی این سند آمده بود، **در کد وجود ندارند** و حذف شدند.

---

## ۵. مدیر تجهیزات (`DeviceManager`)

API واقعی: برای هر تجهیز `…On()` / `…Off()` / `…Toggle()` / `…State()`،
به‌علاوهٔ `begin()`، `update()` و `allOff()`.

> ⚠️ متدهای `controlDevice()`، `getDeviceStatus()`، `protectionCheck()` در کد نیستند.

**محافظت‌های واقعی (طبق کد):**
- **محافظت آب خالی (`waterEmpty`):**
  - پمپ و مه‌ساز بلافاصله **خاموش** می‌شوند
  - دستور روشن‌شدن دوبارهٔ آن‌ها **رد (blocked)** می‌شود
  - در منطق اتوماسیون هم روشن‌شدن خودکار آن‌ها مشروط به `!waterEmpty` است
- **حالت ایمن (Safe Mode):** اگر DHT22 بیش از **۱۲۰ ثانیه** معتبر نخوانده شود،
  فن/پمپ/مه‌ساز خاموش نگه داشته می‌شوند و منطق دما/رطوبت/زمان‌بندی برای آن‌ها نادیده گرفته می‌شود
  (**روشنایی مستثناست**)
- **محدودیت بازهٔ تغییر:** `canChangeState()` جلوی سوییچینگ خیلی سریع را می‌گیرد
- **ساعت نامعتبر:** تا قبل از همگام‌سازی NTP، زمان‌بندی‌ها اعمال نمی‌شوند
  (`now > 1700000000` به‌عنوان شرط اعتبار)

## ۶. منطق اتوماسیون (`AutomationManager`)

**نوع الگوریتم:** کنترل **مبتنی بر آستانه + زمان‌بندی ساعتی** (روشن/خاموش)

> ❌ **کنترل PID، یادگیری تطبیقی، موتور قانون (`addRule`) و «هدف ۲۲–۲۶ درجه / ۶۰–۸۰٪»
> در کد پیدا نشدند** و از نسخهٔ قبلی حذف شدند.

### آستانه‌ها و زمان‌بندی

کنترل دستگاه بر اساس آستانه‌های دما و رطوبت و زمان‌بندی انجام می‌شود؛ مقادیر دقیق در مستندات خصوصی نگهداری می‌شوند.

**سایر نکات:**
- اتوماسیون در پیکربندی فعلی فعال است
- ساعت از NTP همگام می‌شود (`pool.ntp.org`، اختلاف `12600` ثانیه = GMT+3:30)
- زمان‌بندی‌ها فقط وقتی معتبرند که زمان از NTP همگام شده باشد

### سطح آب (نسخهٔ `g-vs-bly`)
- آستانه‌های خالی/پر بودن مخزن و آستانهٔ هیسترزیس به‌صورت مقدار خام ADC تعریف شده‌اند؛
  مقادیر دقیق در مستندات خصوصی نگهداری می‌شوند

## ۷. ارتباط Blynk

### Virtual Pin های واقعی (از `Datastreams.h`)

| پین | نقش |
|---|---|
| `V0` | روشنایی (Light) |
| `V1` | دما |
| `V2` | رطوبت |
| `V3` | مه‌ساز (Fogger) |
| `V4` | فن (Fan) |
| `V5` | پمپ (Pump) |
| `V6` | سوییچ حالت AUTO / MANUAL |
| `V7` | سطح آب مخزن (٪) |
| `V8`–`V11` | رزرو (در کد کامنت‌شده) |

> ⚠️ نگاشت قبلی («V1: حالت، V2: دما، … V9: خطاها») **با کد ناسازگار بود** و اصلاح شد.

## ۸. رابط وب محلی (`WebUIManager`) — فقط در `g-vs-bly-loc1`

رابط وب محلی دارای قابلیت مشاهده وضعیت و ارسال فرمان است؛ جزئیات پیاده‌سازی در مخزن خصوصی نگهداری می‌شود.

**وضعیت احراز هویت:** مشاهده (2026-10-09): **هیچ احراز هویتی در منابع موجود دیده نشد** — رابط پذیرندهٔ فرمان‌های کنترلی تجهیزات است؛
خطر آن است که هر دستگاهِ همان شبکه بتواند تجهیزات را کنترل کند (مشکل **حل‌نشده**).
این مورد یک **تصمیم باز** است و **نیازمند تعیین تکلیف امنیتی توسط مدیر پروژه** است.
تا پیش از آن تصمیم، **نباید** نه وجود احراز هویت و نه عدم وجود قطعی آن به‌عنوان وضعیت نهاییِ پذیرفته‌شده معرفی شود.

> هماهنگ با `ARCHITECTURE.md` ← بخش «امنیت نرم‌افزاری».
> در فهرست تعارض‌ها: `STATUS.md` و `VALIDATION-REPORT.md` ← مورد ۱۰.

## ۱۰. مقایسهٔ دو نسخهٔ کد

| ویژگی | `g-vs-bly` | `g-vs-bly-loc1` |
|---|---|---|
| تاریخ آخرین تغییر (طبق مخزن) | 2026-10-05 | 2026-10-07 |
| رابط وب داخلی (WebUI) | ❌ ندارد | ✅ دارد (⚠️ **بدون احراز هویت**) |
| OTA | ❌ ندارد | ✅ دارد |
| کنترل/تداوم فن ۴سیمه (`FAN_PWM`, `FAN_TACH`) | ❌ | ✅ (⚠️ `FAN_PWM=GPIO4` با پین سنسور آب در `g-vs-bly` تداخل دارد) |
| پین `DHT22` | `17` ✅ (مطابق مرجع) | `21` ❌ (انحراف از مرجع) |
| پین سنسور آب | `4` ✅ (مطابق مرجع) | `17` ❌ (انحراف از مرجع) |
| خواندن سنسور آب | `analogRead` (آرایه‌ای) | `digitalRead` + `INPUT_PULLUP` (کلید شناور) |

> ✅ **به‌روزرسانی (2026-10-09):** مرجع پین‌ها با ۶ منبع مستقل تثبیت شد: `DHT22=GPIO17`, `WATER=GPIO4`.
> انحراف‌های `g-vs-bly-loc1` از مرجع ثبت شدند، نه به‌عنوان طرف برابر یک تعارض.

**وضعیت مقایسه با مرجع:**
- `g-vs-bly` → **پین‌ها مطابق مرجع**؛ نوع خواندن سنسور آب هنوز مورد مناقشه است (بند ۳.۱)
- `g-vs-bly-loc1` → **نوع خواندن با مشخصات فیزیکی HDD v1.0 هم‌خوان**؛ اما **پین‌ها از مرجع انحراف** دارند

> **تصمیم لازم از مدیر پروژه:** کدام نسخه مرجع اجراست؟ سپس پین‌ها و نوع سنسور در نسخهٔ منتخب همسان می‌شوند.
> جزئیات: `STATUS.md` (جدول تعیین تکلیف) و `docs/hardware-overview.md` (بندهای ۳.۱، ۳.۲، ۳.۸).

## ۱۱. لاگ و تشخیص خطا

- `monitor_speed = 115200`
- `CORE_DEBUG_LEVEL=0` → لاگ‌های debug فریم‌ورک خاموش‌اند
- خروجی‌های `Serial` برای پیام‌های تشخیصی (مثل پیام‌های OTA) استفاده می‌شوند

> ⚠️ سطوح لاگ `ERROR/WARNING/INFO/DEBUG` به‌عنوان یک سیستم ساختاریافته،
> و همچنین «ارسال لاگ به Blynk Cloud» و «فایل لاگ محلی» در کد پیدا نشدند.
